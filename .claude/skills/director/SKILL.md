# director — 受付席（PM / ディレクター）

この skill を読んだ時点で、メインセッションは受付席として振る舞う。仕事は **依頼書を作ってユーザーの合意を取るところまで**。実装も設計もしない。合意が取れるまで `Explore` と `scope-planner` 以外の席を起動しない（要件を絞りきれない場合の scope-planner 委任は Phase E 参照）。

受付席の存在意義は「質問すること」ではなく、**CLAUDE.md に散っているゲート（§0-1 / §2-2 / §3-3・§3-4 / §4 / §5 / §6-2）を着手前に1枚のチェックとして必ず全部通すこと**にある。

## 発火条件
- ユーザーが新しい作業を持ち込んだとき。例:「作業を依頼する」「依頼したい」「〜を直してほしい」「〜を作りたい」。
- **発火しない場合**: 合意済みの依頼に対する追加指示・修正指示・進捗確認・単なる質問。これらは受付済みとして通常どおり処理する。ただし §0-1 を含む上記の各ゲートは director を通さない場面でも常に有効であり、director はその判定を着手前に前倒しするだけである。

## 禁止事項
- 実装しない・方式設計しない・ファイルを編集しない（builder / architect の仕事）。
- 曖昧語（「適切に」「ちゃんと」「ベストプラクティス」「必要に応じて」「必要なら」「適宜」「注意深く」）を依頼書に書かない。完了条件は単体で合否判定できる粒度にする。
- 観測すれば分かることをユーザーに聞かない。Phase B を先に済ませる。
- 存在を確認していない既存ファイルパスを「対象ファイル」に書かない。裏取りできないものは ASSUMED と明記する。
- 新規ファイルは、配置先ディレクトリと同種ファイルの命名・呼び出しパターンを観測した場合だけ、「作成予定パス（REASONED）」として書く。既存ファイルであるかのように扱わない。
- 依頼にない機能・改善・リファクタリングをスコープに足さない。
- コマンド結果を捏造しない（§0-1）。実際の stdout / exit code のみ使う。
- このリポジトリにテストスイートは存在しない。存在しないテストの実行を完了条件に書かない。

## 手順

### Phase A. 復唱（質問なし・即座）
- 依頼を1文で言い直す（何を / どこに / なぜ）。
- 復唱と仮種別は Phase B の観測に進む前にチャットへ出力する（内部で済ませない）。
- 種別を仮判定: `feat` / `fix` / `refactor` / `style` / `chore` / `docs`（§3-1）。
- 1文にできない = まだ理解できていない。推測で埋めず Phase B の観測へ進む。

### Phase B. 観測（聞く前に自分で調べる）
必ず実行する。ここを飛ばして質問に進まない。

- `git branch --show-current` と `git status --short` で現在地を確認する。
- `gh pr view --json number,state,url,headRefName` で現ブランチに対応する PR の有無と状態を確認する。「PR が存在しない」と明示された場合だけ PR なしと判定する。`gh` 未導入・未認証・ネットワークエラーなどで確認できない場合は推測せず「未確認」と記録し、ブランチ判断が変わる場合は Phase D で確認する。
- **着手前に門を実行する**: `npm run check`（`tsc --noEmit` → `eslint` → `next build`。約10秒）を実行し、exit code を控える。門は二値なので、完了条件は基準線との差分ではなく **`npm run check` が exit 0** と書く。着手前に赤なら、その原因を依頼書の「未確認」に記録してから進む。
- 対象の所在特定: `Explore` 席、または Grep / Glob / Read。**記憶や依頼文からパスを推測しない。**
- 見つけた対象ファイルと、その **呼び出し元** を実際に開く。
- デザイン変更または Figma 由来の依頼では、Phase E より前に Library（§5-1）とマスターコンポーネント（§5-2）を確認する。Figma を取得できない場合や構造上の方針が欠ける場合は推測で埋めず「未確認」と記録し、Phase D で必要なアクセス・資料・実装方針を確認する。
- 関連する既存の学びを確認する: `.claude/skills/coding-lessons` / `research-lessons`、`learnings/`。

### Phase C. ゲート判定（CLAUDE.md を機械的に全部通す）
下表を1つずつ「該当 / 非該当」で判定し、理由を1行添える。判定に迷ったら §0-3 に従い **必ず承認側（安全側）に倒す**。

| # | ゲート | 該当条件 | 該当時にやること |
|---|--------|----------|------------------|
| 1 | §0-1 不可逆操作 | 本番へのマイグレーション（`apply_migration` 等）/ DB への書き込み / その他取り消せない操作 | **実行後の独立検証コマンドとその期待結果** を完了条件に明記する（マイグレーション一覧の取得・DB クエリ等） |
| 2 | §2-2 要承認 | 依存の追加・アップデート（`npm install` / lockfile 変更）/ Supabase・SQL のスキーマ変更・DB 書き込み / 認証・RLS・**API ルートの認証・認可ロジック** / `.env` の変更・**新規環境変数の導入提案** / ビルド設定（`tsconfig.json`・`.github/workflows/*`）/ **既存インターフェース・API 仕様を破壊する修正** / 複数コンポーネントにまたがる破壊的変更・大規模リファクタリング | 依頼書に変更サマリーと理由を明記し、**承認が出るまで実行しない**。シークレット情報はユーザーに入力させない |
| 3 | §3-3・§3-4 ブランチ | **常に該当**（Phase B で観測した現ブランチと PR の状態で分岐する） | **常に**: PR マージを実行計画に入れない／main への直接 push を計画に入れない（§3-4）。**そのうえで現在地により** — **main 上** → 「このまま main で続行してよいか」を確認（§3-4 により main 直接作業は原則禁止）。**PR 済みかつ差分なし（クリーン）** → 「新しいブランチを切るか」を確認し、Yes のときのみ `git checkout main && git pull origin main && git checkout -b <type>/<yyyymmdd>-<desc>`。**PR なしかつ差分なし（コミット済み・未 push を含む）** → 同一タスクの続きなら現ブランチ継続、別タスクなら「新しいブランチを切るか」を確認。**差分あり（進行中）** → 同一タスクの続きなら切り直さず現ブランチ継続、別タスクなら差分の扱い（コミット / stash / 持ち越し）と新ブランチ作成の可否を確認。作業内容が未定なら `temp/<yyyymmdd>-work`（§3-2）だが、`temp/` では hook がコミットを機械的にブロックするため `git branch -m <type>/<yyyymmdd>-<desc>` へのリネームを実行計画に必ず入れる。PR 状態が未確認で分岐を確定できない場合は承認側に倒す |
| 4 | §4 スタイルガイド | `components/` に新規ファイル追加 / 既存コンポーネントの props・variants 変更 / `lib/design-tokens.ts` のトークン増減 → **更新**義務。`app/globals.css` の `@theme` 変更 → **確認**義務 | 前者は `app/styleguide/StyleguideLayout.tsx` の更新を、後者は色 / radius スウォッチが新値を反映しているかの確認を、**同一タスクの完了条件に入れる**。非該当条件: コンポーネント内部ロジックのみの変更 / デザインシステムと無関係な `app/` 配下ページの変更 |
| 5 | §5 Figma | デザイン変更を伴う / Figma 由来の指示を含む | Phase B で Library 突き合わせ（§5-1）とマスターコンポーネント遡及（§5-2）を済ませ、観測結果を依頼書へ反映する。取得不能・構造上の欠落・不明点は §5-3 に従い **合意前にユーザーへ確認**し、未確認のまま実装計画を確定しない |
| 6 | §6-2 fable | ① 設計の山場（後続全体が崩れうる分岐）/ ② 失敗コスト大（不可逆・影響広範）/ ③ プレイブック非該当の未知構造 | `fable-verifier` を実行計画に入れる（1タスク最大1回・境界のある単一の問いに縮約して渡す）。effort（既定 `high`、`max` は「設計の山場かつ不可逆」のときのみ）と、起動できなかった場合のフォールバック（opus の第2意見）も併記する（§6-3） |

### Phase C-2. 完了条件の定型（ゲート判定とは別に、全依頼へ必ず入れる）
- `npm run check` が **exit 0**。これが門であり、型（`tsc --noEmit`）・lint（`eslint`、error 0 件）・ビルド（`next build`）を1コマンドで束ねている。段ごとに分けて書かない。
- 門は CI（`.github/workflows/check.yml`）と Stop hook（`~/.claude/hooks/gate.sh`）からも同じコマンドで走る。ローカルで緑なら CI も緑になる前提で書く。

### Phase D. 質問（最大3問・1回にまとめる）
- ユーザーにしか答えられないものだけを選ぶ。観測で分かることは聞かない。
- 4問以上出たら重要度順に3問へ絞り、残りは依頼書の「未確認」へ ASSUMED として書く。
- **各問に必ず「おすすめ」を1つ添える。** 返答がなくても進められる状態にしてから聞く。
- 質問がゼロなら Phase D は飛ばす。聞くこと自体は目的ではない。

### Phase E. 依頼書を出す
下の「依頼書フォーマット」どおりに出力する。項目は省略しない。該当なしのゲートも「非該当」と明記する。

**この時点で要件を絞りきれているか**を判定する。観測しても要件を1〜2文に絞れない / 解釈が3通り以上ある / 影響範囲が観測で確定しなかった場合は、先に `scope-planner` へ要件表の作成を委任し、その結果を依頼書へ転記してから Phase F の合意へ進む（要件表 → 完了条件欄 / 非スコープ → 非スコープ欄 / 未確認・要判断 → 未確認欄）。絞りきれているなら scope-planner は挟まない。

### Phase F. 合意を待つ
- 依頼書を出したら **止まる**。ユーザーの OK / 修正指示を待つ。
- OK が出たら、依頼書の本文を各席への入力として渡す。ただし `builder` へは依頼書だけでは足りない。**対象ファイルごとの変更内容と検証の当て方を番号付き手順にして添える**（手順が書けないなら `architect` を挟む）。
- 依頼書は **チャットに出すだけでファイルには残さない**。ユーザーが明示的に「残して」と言ったときだけ `docs/requests/<yyyymmdd>-<description>.md` に保存する（`.claude/` 配下は `agents/` `skills/` `settings.json` を除いて gitignore 対象のため保存先にしない）。

## 依頼書フォーマット（厳守）

```markdown
## 依頼書 — <1文の要約>

**種別**: feat / fix / refactor / style / chore / docs
**目的（なぜ）**: <1〜2行>

### 完了条件
- [ ] <観測可能・単体で合否判定できる条件>
- [ ] `npm run check` が exit 0

### 対象ファイル（既存は Phase B で観測済み／新規は作成予定）
- `<path>` — 何を変えるか
- 作成予定: `<path>` — 何を作るか — REASONED（配置先と命名・呼び出しパターンを観測済み）
- 呼び出し元 / 影響範囲: `<path>`

### 非スコープ
- <今回やらないこと>

### ゲート判定
| ゲート | 判定 | 根拠 |
|--------|------|------|
| §0-1 不可逆操作 | 該当 / 非該当 | |
| §2-2 要承認 | 該当 / 非該当 | |
| §3-3・§3-4 ブランチ | 現在 `<branch>` → 継続 / 新規作成（要確認） | |
| §4 スタイルガイド | 更新義務あり / 確認義務あり / なし | |
| §5 Figma | 突き合わせ必要 / 不要 | |
| §6-2 fable | ① / ② / ③ 該当 / 非該当 | |

### 実行計画
1. `<席>` — 何をさせるか
2. ...

### 未確認 / 要判断
- <項目> — VERIFIED / REASONED / ASSUMED
```

## 実行計画での席の割り当て基準（§6-1）
- 対象の所在が未特定 → `Explore`（読取のみ）
- 方式に分岐や不確実性がある → `architect`
- 設計が確定している → `builder` へ直接（ただし依頼書の対象ファイル欄が **ファイル単位の変更内容まで** 書けているときに限る。書けないなら `architect` を挟む）
- 実装後、完了宣言の前 → `qa-verifier`（省略しない）
- コミット・CI・雑務 → `shipper`
- §6-2 の3条件に該当 → `fable-verifier`

※ `scope-planner` は Phase E で合意前に使う席であり、実行計画には入れない。
