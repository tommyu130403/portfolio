# 運用リファクタの反映順序

この作業ブランチはコードと SQL ファイルの準備まで。Supabase の実データと公開サイトは変更していない。

## 変更の目的

- ゲスト用パスワードをブラウザー内で照合する方式を廃止し、Supabase Auth のメールアドレス＋パスワードと DB の閲覧許可リストでプロフィール・経歴・作品などの行を保護する。
- 管理者だけが作品本体とスキル・ツールの関連を一括保存できるようにする。途中で失敗したら DB 側で全体を取り消す。
- Markdown の先頭本文、プロフィール表示、読み込み・削除・並び替え失敗時の表示、画像一覧の 1,000 件制限を修正する。

## 依存する別作業と適用順序

1. 統合済みの `feat/20261020-work-categories` に含まれる `20261020120000_work_categories.sql` を開発環境で先に適用し、カテゴリの読み書きを確認する。閲覧制限 SQL はこのテーブルがない場合に停止する。本番でも新しいフロントを反映する前に同じマイグレーションを適用する。
2. 既存の管理者ログインが書き込めることを確認する。
3. `20261020130000_prepare_reader_access.sql` と `20261020130500_atomic_work_save.sql` のみを開発環境で適用する。ここでは匿名読み取りをまだ閉じない。
4. Supabase Auth にゲスト専用ユーザーを作り、その `user_id` だけを `private.readers` に登録する。パスワードを SQL・ソース・ログに保存しない。ゲスト、管理者、未登録のログインで `portfolio_access_role()` がそれぞれ `reader`、`owner`、`denied` を返すことを確認する。
5. 新しいフロントを開発環境で動かし、ゲストは公開作品のみ、管理者は下書きと編集画面を利用できること、一括保存が失敗時に巻き戻ることを確認する。その後フロントを本番へ反映する。
6. `20261020131000_protect_portfolio_reads.sql` を適用する。別の読み取り操作で、匿名では対象 12 テーブルが 0 行、ゲストでは `works` とその関連が公開作品分のみ、管理者では下書きも読めることを確認する。本番への SQL 適用・アカウント作成・公開は、このブランチ作成の承認に含まれない。

一括 `db push` で保留中のマイグレーションをすべて流すと、フロント反映より先に匿名読み取りが閉じる。上の段階ごとに適用対象を確認する。

## 残る運用上の論点

- `Portfolio` Storage バケットと保存済みの公開画像 URL は引き続き公開される。画像自体も保護する場合は、非公開バケット、署名付き URL、既存 URL の移行を別途設計する。
- ゲストはログイン後、フローチャートや語彙表などの作品以外のテーブルを全件読める。ゲストにも下書き専用データを見せない要件がある場合、それらの公開状態を表す列や関連を追加してポリシーを絞る。
- SQL は実 DB で未検証。開発環境で匿名・ゲスト・管理者の読み書き境界を確認してから本番へ進める。失敗時は公開読み取りを戻して情報を再公開するのではなく、反映を止めて権限またはフロントを修正する。
- `src/types/supabase.ts` にはカテゴリ作業ブランチの生成型を統合した。今回追加した SQL は実 DB に未適用のため、適用後に `npm run update-types` で型を再生成し、RPC の一時的なローカル型を外す。
- `app/admin/AdminLayout.tsx` から作品一覧と共通見出しは分離済み。プロフィール・経歴・スキルなど残る画面の分割は今回の機能統合と分けて進める。
- 静的配信では使われていない `/api/proofread` の整理と依存パッケージ更新は別作業。2026-10-20 の `npm audit --omit=dev` は本番依存に 1 件の critical、5 件の high、1 件の moderate を報告した。静的配信での実際の影響は個別に評価する。
