# サイトの重さと画像のぱらつき — 原因一覧と修正方針(2026-11-03)

対象: 公開ページ(トップ `/`・作品一覧 = トップ内 `#works`・作品詳細 `/works?id=…`)。
コードは変えていない。数値はすべて「修正前」。

## 結論

重さの正体は **JS の処理の重さではなく、通信の待ち行列** である。長時間タスク(50ms 超の処理)は全ページで 0 件だった。
一方で、ページが見えるまでに「ログイン確認 → 権限確認 → データ取得 → 画像の署名 → 画像取得」が **直列** に並び、画像は **1 枚ごとに署名の往復** をしてから読み込むため、1 枚ずつ時間差で現れる。これが「ぱらつき」の正体である。

| 順位 | 原因 | 影響 | 直す手間 |
|---|---|---|---|
| 1 | 画像を 1 枚ずつ署名してから読む(見えてから表示まで 0.8〜1.7 秒) | ぱらつきの主因 | 中 |
| 2 | 画像ファイルが表示サイズに対して大きすぎる(最大 3.2 MB を 159px 幅で表示) | 読み込みの遅さ・通信量 | 小〜中 |
| 3 | 同じ画像を 2 回取得している(署名 URL が毎回変わりキャッシュが効かない) | 詳細ページの遅さ | 小 |
| 4 | フォント 156 ファイル 1.7 MB。うち約 1 MB は本文で使っていない M PLUS 1p の先読み | 初回表示の遅さ | 小 |
| 5 | データを全部ブラウザ側で取る(本文が出るまで 1.1〜1.6 秒・そのあと大きくレイアウトがずれる) | 体感の遅さ・CLS 0.21〜0.23 | 中〜大 |
| 6 | 作品詳細は取得が 2 波に分かれ、主画像の署名がその後ろに付く(LCP 3.4 秒) | 詳細ページの遅さ | 小 |
| 7 | スクロール処理・smooth scroll・`transition-all` | 実害なし(長時間タスク 0) | — |

## 原因の詳細(影響の大きい順)

### 1. 画像を 1 枚ずつ署名してから読む(ぱらつきの主因)

- **何が起きているか**: 画像は非公開バケット(`Portfolio`)にある。`components/ProtectedImage.tsx` は、画像が画面に入った(手前 200px)ときに初めて署名 URL を 1 枚ずつ取りに行き(`createSignedUrl`)、届いてから `<img>` に URL を入れる。署名の往復(0.1〜0.5 秒)の後に画像の取得(0.5〜1.3 秒)が始まるので、同じ行の画像でも揃わず、順不同で現れる。
- **根拠**: 作品一覧で署名 17 回、見えてから表示まで中央値 1.14 秒(上表)。スクロール 1 秒後の空白スクリーンショット。
- **場所**: `components/ProtectedImage.tsx:61-90`(IntersectionObserver → `createSignedUrl`)。利用元: `WorkThumbnail.tsx` / `WorkCard.tsx` / `WorkDetailHeader.tsx` / `WorkPagerCard.tsx` / `WorkMarkdown.tsx` / `DeviceMock.tsx`。

### 2. 画像が表示サイズに対して大きすぎる

- **何が起きているか**: 一覧のサムネイルは 155×123px 程度で表示されるのに、元ファイルは 1,600px 幅の PNG(0.8〜1.2 MB)や、**13,360×5,840px・3.2 MB** の PNG(`image_1792477123979.png`、表示は 159×131px)が混じる。`next.config.ts` が `images.unoptimized: true`(静的書き出しのため)なので Next.js 側の縮小は効かず、`<img>` 直書きで原寸を落としている。
- **根拠**: 一覧 14 枚で 6.2 MB、詳細 8 ファイルで 4.8 MB。主画像 `pf-cts-lp-pc.png` 1,151 KB(1600×707 を 356×223 で表示)。
- **場所**: Storage 上のファイル本体(コードではない)。`components/ProtectedImage.tsx` は幅・高さ・`srcset` を持たない。

### 3. 同じ画像を 2 回取得している

- **何が起きているか**: 署名 URL は呼ぶたびにトークンが変わるため、ブラウザのキャッシュが効かない。詳細ページでは主画像(PC/SP の 2 枚)が **1,062 ms と 2,562 ms の 2 回** 署名・取得されている(再描画で `ProtectedImage` が作り直されたため)。前後ナビのカードも、同じ画像を別インスタンスがそれぞれ署名している(`career-ticket-scout-white.png` と `image__6….webp` が各 2 回)。
- **根拠**: 詳細ページのリソース記録(12 回取得 / 実体 8 ファイル、2.1 MB が重複分)。
- **場所**: `components/ProtectedImage.tsx` は署名結果をコンポーネント内 state にしか持たない(共有キャッシュなし)。`components/WorkDetailClient.tsx:140-156` の第 2 波の取得で `order` state が更新され、その再描画で主画像が作り直される(REASONED: 2 回目の署名時刻 2,562 ms が第 2 波の完了直後)。

### 4. フォントが 156 ファイル・1.7 MB

- **何が起きているか**: `app/layout.tsx` で Google Fonts 5 書体を `next/font` で読み込む。日本語フォントは 120 本超の分割ファイルになる(Noto Sans JP 248 本・M PLUS 1p 252 本の `@font-face`)。トップの HTML には **124 本の `<link rel=preload>`** があり、うち **M PLUS 1p 700 が 119 本・959 KB**。しかしトップ・詳細で実際に描画に使われた書体は Noto Sans JP / Afacad / Figtree だけで、**M PLUS 1p は使われていない**(`document.fonts` の loaded 一覧に無い)。
- **根拠**: 読み込み済み 156 ファイル 1,733 KB の内訳: M PLUS 1p 700(先読み)119 本 959 KB / Noto Sans JP 700 32 本 671 KB / その他 5 本 104 KB。
- **場所**: `app/layout.tsx:14-20`(M PLUS 1p、`subsets: ["latin"]`、`preload` 未指定=既定 true)。`app/globals.css:74-76`(`--font-guide` / `--font-mplus`、公開ページの部品からは参照なし。ログイン画面の氏名のみ `font-mplus`)。

### 5. データを全部ブラウザ側で取る

- **何が起きているか**: 静的書き出しのため HTML に本文が無く、`AuthGate` が「セッション確認 → 権限確認(RPC)→ 本文」の順で初めて描画する。権限確認が **初回 0.6〜0.8 秒**、そのあと 9 クエリを並列で投げて 0.4 秒。本文が出るのは 1.1〜1.6 秒後で、そのとき空だった領域が一気に伸びる(CLS 0.21〜0.23)。
- **根拠**: トップのリソース記録(`portfolio_access_role` 98→922 ms、9 クエリ 956→1,561 ms)。CLS の発生源は `SECTION.w-full max-w-main`。
- **場所**: `components/AuthGate.tsx:9-11`(確認中は空の `<div>`)、`lib/auth.tsx:60-78`(RPC)、`app/page.tsx:52-65`、`src/components/WorksList.tsx:28`、`components/SkillsCardGrid` ほか。

### 6. 作品詳細の取得が 2 波+主画像が後回し

- **何が起きているか**: 第 1 波(本文 5 クエリ)の後、前後ナビ用の `works` 取得が第 2 波として走り、主画像の署名はそれと同時(1,062 ms)に始まる。主画像が出るのは 2.2 秒、再取得込みで LCP は 3.4 秒。
- **根拠**: 詳細ページのリソース記録。LCP 要素は `IMG.aspect-[16/10]`(`pf-cts-lp-pc.png`)。
- **場所**: `components/WorkDetailClient.tsx:74-137`(第 1 波)/ `:140-156`(第 2 波)。

### 7. 実害が確認できなかったもの

- `app/page.tsx:104-122` のスクロールごとの `getBoundingClientRect` + `setState`、`app/globals.css:40` の `scroll-behavior: smooth`、`transition-all` 4 箇所: 長時間タスク 0 件、50ms 超のイベント 0 件。今回の計測では「カクつき」は再現しなかった(ローカル・M 系 Mac。低スペック端末は未確認)。

## 修正方針(案ごとの効果と手間)

| 案 | 対象原因 | 内容 | 効果 | 手間 |
|---|---|---|---|---|
| A. 署名を一覧ぶんまとめて 1 回で取る | 1 | 一覧・詳細のデータ取得の直後に `createSignedUrls`(複数パス一括)を 1 回呼び、結果を画面全体で共有する。画像ごとの往復(0.1〜0.5 秒 × 枚数)が消え、画像の取得が同時に始まる | 大 | 中(ProtectedImage の受け口と呼び出し元の変更) |
| B. 署名結果を共有キャッシュにする | 3 | パスをキーに署名 URL(有効 1 時間)をモジュール内 Map で共有。同じ画像の二重署名・二重取得が消える | 中(詳細 −2.1 MB) | 小 |
| C. 画像を表示サイズに合わせて縮小・WebP 化 | 2 | Storage のファイルを、サムネイル用(幅 400px 程度)と本文用(幅 1,600px)に分けて書き出す。13,360px の PNG は再出力必須。Supabase の画像変換(`transform`)は有料プラン機能のため、まずはファイル側で対応 | 大(一覧 6.2 MB → 推定 1 MB 未満) | 中(画像の再出力・再アップロードは手作業) |
| D. 表示の「待ち」を見せる | 1 | 署名待ち・取得中はぼかしの低解像度版か、面積固定の薄い地(現状は地だけ)。画像到着時にフェードイン。順不同でも「壊れている」ように見えなくなる | 中(体感) | 小。**見た目が変わるので要デザイン判断** |
| E. M PLUS 1p の先読みをやめる | 4 | `preload: false` にするか、公開ページで使っていないなら `layout.tsx` から外しログイン画面だけ読む。Noto Sans JP も使う太さだけに | 中(初回 −1 MB) | 小 |
| F. 本文領域の骨組み(スケルトン)を先に描く | 5 | `AuthGate` の空 `<div>` と各セクションの読み込み中に、最終的な高さに近い枠を出す。CLS が下がり、空白時間が「読み込み中」と分かる | 中(CLS 0.2 → 0.05 目安) | 小〜中。**見た目が変わるので要デザイン判断** |
| G. 詳細の取得を 1 波にし、主画像を最優先 | 6 | 前後ナビ用の `works` 取得を第 1 波に合流。主画像の署名を本文取得と同時に始める(本文の `thumbnail_url` が分かった時点) | 中(LCP 3.4 → 推定 1.5 秒) | 小 |
| H. 権限確認の往復を減らす | 5 | 初回 RPC が 0.6〜0.8 秒(接続確立込み)。役割を JWT のカスタムクレームに入れればブラウザ側で判定でき往復ゼロ。ただし Auth の設定変更(§2-2 要承認) | 中 | 中。**認証まわりの変更なので要承認** |
| I. 公開してよい画像は公開バケットに戻す | 1,3 | 署名そのものが不要になり、ブラウザと CDN のキャッシュも効く。閲覧制限の方針と衝突するため、方針判断が先 | 大 | 小(技術)/ **方針判断が必要** |

推奨の順番: **E(小・確実)→ B → G → A → C → D/F(デザイン判断の後)**。H と I は方針を決めてから。

## 画像のぱらつきへの個別改善案(まとめ)

1. **一括署名(A)+ 共有キャッシュ(B)**: 1 枚ずつの往復をなくす。これだけで「見えてから表示まで」の署名ぶん(0.1〜0.5 秒)と重複取得が消える。
2. **サムネイル専用の小さい画像(C)**: 一覧 14 枚 6.2 MB を 1 MB 未満へ。取得時間(0.5〜1.3 秒)が数分の一になる。
3. **到着の見せ方(D)**: フェードインと低解像度プレースホルダ。順不同でも気にならない見た目に。デザイン判断が要るため今回は提案のみ。
4. **主画像の先行署名(G)**: 詳細ページの主画像だけは、本文より先に出す。

## 未確認・計測の制約

- Lighthouse の点数は未取得(`npx lighthouse` の一時実行が自動モードで拒否)。代わりに Chrome の Performance API で LCP・CLS・長時間タスク・リソース記録を採った。
- 回線はローカル(高速)。実ユーザーの LCP・表示待ちは、ここに回線分が上乗せされる。
- モバイル 375px の FCP/LCP は擬似環境で取得できなかった。詳細ページの主画像もモバイルでは 7 秒時点で未取得(原因未確認)。
- 転送量(gzip 後)は Supabase 側の応答に `Timing-Allow-Origin` が無いため記録から取れず、画像は HEAD で `content-length` を、JS/CSS は手元で gzip して算出した。
- 低スペック端末での「カクつき」は再現していない(長時間タスク 0 件)。
- `.env.local` の本番用公開キーは古い形式(JWT)で、本番プロジェクトは 401 で拒否する。計測では本番サイトに埋め込まれている新形式の公開キー(`sb_publishable_…`)をビルド時に指定した。`.env.local` の更新はユーザー作業(§0-2)。

## 付録: 再計測の手順

1. `npm run build`(本番サイトと同じ公開キーを `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY` で渡す)
2. `out/` を `www/portfolio` にコピーし `node docs/perf-audit-2026-11/serve.mjs www 8765`
3. ブラウザで `http://localhost:8765/portfolio/` を開きログイン
4. DevTools の Console で `performance.setResourceTimingBufferSize(3000)` を最初に実行(既定 250 件ではフォントだけで溢れる)
5. `performance.getEntriesByType('resource')` を `supabase.co` で絞り、`initiatorType` が `fetch`(署名)と `img`(画像)の `startTime` / `responseEnd` を比べる
