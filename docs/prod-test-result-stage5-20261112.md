#### 決定と運用(2026-11-12)
オーナーが「どちらも GitHub の Actions(自動処理)で自動化する。控えの保存先は非公開リポジトリ」と決めた。

| 自動処理 | いつ | 何をするか | 使う秘密 |
|---|---|---|---|
| `Supabase keep-alive`(`.github/workflows/supabase-keepalive.yml`) | 毎日 09:17 ごろと 21:17 ごろ(日本時間。GitHub の都合で遅れることがある) | 公開の鍵(サイトが誰にでも配っている読み取り用の鍵)で `profile` 表を 1 回読む。データベースが正常に答えたら成功 | 既存の `NEXT_PUBLIC_SUPABASE_URL`・`NEXT_PUBLIC_SUPABASE_ANON_KEY` |
| `Supabase backup`(`.github/workflows/supabase-backup.yml`) | 毎月 2 日 03:40 ごろ(日本時間) | `supabase db dump` で「利用者の役割」「表の構造」「中身のデータ」の 3 ファイルを書き出し、非公開リポジトリ `portfolio-db-backups` に日時の名前のフォルダで保存する | `SUPABASE_DB_URL`・`BACKUP_REPO_TOKEN`(オーナーが登録) |

##### 最初の設定(オーナーが 1 回だけ行う。これが無いと控えの処理は失敗する)
1. GitHub で新しいリポジトリ `portfolio-db-backups` を作る。**必ず「Private」(非公開)を選ぶ。**
2. GitHub の右上のアイコン → Settings → Developer settings → Personal access tokens → Fine-grained tokens で鍵を作る。「Repository access」は `portfolio-db-backups` だけ、「Permissions」の Contents は「Read and write」。期限は 1 年を目安にする。
3. Supabase の管理画面で「Connect」→「Session pooler」の接続文字列を写す(GitHub の実行環境からは、もう一方の「Direct connection」ではつながらない)。`[YOUR-PASSWORD]` をデータベースのパスワードに置き換える。パスワードに記号が入っているときは、Claude に置き換え方を聞く(パスワードそのものは Claude に見せない)。
4. portfolio リポジトリの Settings → Secrets and variables → Actions →「New repository secret」で、手順 2 の鍵を `BACKUP_REPO_TOKEN`、手順 3 の文字列を `SUPABASE_DB_URL` という名前で登録する。

##### 運用の注意
- 頻度を週 1 回ではなく 1 日 2 回にした理由: 公式は「1 日に数回の利用で足りる」としており、週 1 回では足りない恐れがあるため。
- 読み取りは権限の規則により 0 件が返るが、問い合わせ自体はデータベースで実行される。公式は判定の詳しい方法を公開していないため、これで止まらないことは運用で確かめる。止まりそうなときは Supabase から警告のメールが来る。
- 控えは公開リポジトリ(このリポジトリ)には置かない。保存の前に、保存先が非公開であることを自動で確かめ、公開なら保存を中止する。
- 控えに含まれないもの: 画像の置き場の中身(`Portfolio` の 75 件)。元の画像を手元に残すか、管理画面から別にダウンロードする。
- 失敗したとき: GitHub から失敗のメールが届く。主な原因は、秘密の未登録、データベースのパスワードの変更、`BACKUP_REPO_TOKEN`(控えを保存するための鍵)の期限切れ。Actions の画面で赤い × の処理を開き、表示を Claude に見せれば原因を調べられる。
- **注意(GitHub の仕様): 公開リポジトリで 60 日間コミットが無いと、定期実行が自動で止まる。** 止まると GitHub からメールが来るので、Actions の画面で「Enable workflow」を押す。
- `BACKUP_REPO_TOKEN` は期限の前に作り直して登録し直す。データベースのパスワードを変えたら `SUPABASE_DB_URL` も登録し直す。
- 控えから戻す手順は公式の [Backup and Restore using the CLI](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) の「Restore backup using CLI」。

### K6: 戻し方の稽古 — 合格

#### 戻し方の手順(計画 §5-2「変更のあとに壊れた」から参照)
1. GitHub でリポジトリの「Pull requests」→「Closed」から、壊した原因と思われる PR を開く。
2. PR の下にある「Revert」ボタンを押す。直前の変更を取り消す新しい PR ができる(この時点では公開中の内容は変わらない)。
3. できた PR の中身が、取り消したい変更だけであることを確かめる(Claude に見てもらってもよい)。
4. オーナーがその PR をマージする。公開処理が自動で走り、約 1 分で公開が終わる。
5. ブラウザは公開中の画面を最大 10 分保存する(サイトの応答に `cache-control: max-age=600` とある)。読み込み直しても古いときは、10 分待つか、ブラウザの保存を消して開き直す。
6. 公開後に K1(5 分の確認)を行う。
7. 原因を直した PR を別に作る。

注意:
- **データベースの変更は、この手順では戻らない。** 戻した PR が DB の変更を伴っていた場合、画面だけが古い形に戻り、DB は新しい形のままになる。DB を戻す命令は別に作り、オーナーが SQL Editor(Supabase の管理画面で命令を打つ画面)で流す必要がある(作品の本文など、データの書き換えも同じ)。
- 実際の取り消しは稽古では行っていない(公開中の内容が変わるため)。「Revert」ボタンが押せるか、押したあとの画面がどうなるかは未確認。
