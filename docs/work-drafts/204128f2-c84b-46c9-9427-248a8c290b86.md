# プロジェクト概要

転職エージェントサービスとスカウト型転職サービスの登録導線を1本にまとめたプロジェクトである。

| 期間 | 2025年7月〜2025年9月(2025年9月29日に本番リリース) |
| 内容 | 転職エージェントサービスの既存登録フォームを廃止した。スカウト型転職サービスのドメインとデータベースを土台に、新しい登録導線を設計し、リリースした。 |

::: figure 新しい導線(1 つの流れで行う)
::: flow highlight=0
- 登録情報の入力
- 判定情報の入力
- 面談予約(通過者)
- 会員登録・認証
- プロフィール入力
:::
:::

# 背景と課題

## 背景

- スカウト型転職サービスの収益性が、目標から大きく乖離していた。
- 転職エージェントサービスも同じ時期に立ち上げフェーズにあり、リソースが分散していた。
- 今後、ブランド全体はエージェントを主軸とするサービスになる方針だった。

## 目的とゴール

::: grid cols=2 gap=4
::: card 目的
登録導線を1本化し、広告費をかけずにスカウト型サービスの登録者データベースを蓄積する。あわせて、両サービスの登録者を最大化する。
:::
---
::: card ゴール
- 新しい登録導線を期日(9月30日目標)までにリリースする。チームのミッションも「期日内にリリースすること」とした。
- 転職エージェントサービスのコンバージョン率と面談設定数を落とさない。
- その上で、スカウト型サービスにも登録される状態をつくる。スカウト側の登録者数のために、他を犠牲にする必要はないとした。
- できるだけ工数をかけずに実現する。
:::
:::

## 課題

- ブランドの転職トップページは、記載がすべてスカウトに関する内容だった。サービスを誤認されるリスクが極めて高かった。企業ロゴの掲載は、優良誤認と取られかねなかった。
- スカウト営業は大きく縮小する方針だった。訴求内容と、実際にスカウトが届く体験との期待値をそろえる必要があった。
- 登録の途中で認証を挟むと、離脱するリスクがあった。
- 途中離脱した人の重複登録や、他人のメールアドレスを入力されるケースへの対策が必要だった。

## スコープ外

次の項目は範囲外とした。

- 判定条件に応じたカレンダー表示の出し分け
- LINE連携
- 既存ユーザーデータの新データベースへの移行
- メールアドレス誤入力時の修正導線
- 退会・メールアドレス変更オペレーションの見直し

## 要件整理

2 サービスの登録フォームを対比表にまとめ、1 本の導線に必要な項目と規則を決めた。

::: figure 要件整理
| フォーム項目 | 両サービスの登録項目を対比し、重複をまとめて統合した |
| 選択肢 | 職種・業界・年収の選択肢も対比し、エージェント基準で統合した |
| 再開 URL | 有効期限を 24 時間に統一した |
| 同一判定 | 同一ユーザーの判定はメールアドレスで行う |
| 既存ユーザー | 過去の登録者のため、スカウト型サービス側のエージェント登録導線は残した |
:::

## フロー設計

::: figure セーブポイント | ここまで入力すると途中再開リンクが届く
::: flow highlight=2
- STEP1 登録情報
- STEP2 判定情報
- 面談予約(通過者)
- STEP3 会員登録・認証
- STEP4 プロフィール
:::
::: caption 1 段目・2 段目フォームの最後をセーブポイントにした。セーブポイント前の離脱では再開リンクが届かない点は、リスクとして整理した
:::

::: figure STEP1〜2: 認証なしで続けて入力 | エージェントの判定項目を先に聞き、1 段目から 2 段目までを途切れなく入力できるようにした
::: mockup phone src=/tmp-preview/img/tenshoku/step1-birthdate.png src=/tmp-preview/img/tenshoku/step2-companies.png
::: caption STEP1 登録情報(生年月日・名前・連絡先)→ STEP2 判定情報(経験社数など)。ここに認証は挟まない
::: grid cols=2 gap=4
::: card 案 1: エージェント項目をすべて必須
面談設定に必要な情報は確実に取れるが、入力の負担が大きく離脱しやすい
:::
---
::: card 案 2: 判定項目までを必須
面談日程調整とスカウト側の項目は任意にして、登録の完了を優先する
:::
:::
::: caption 必須項目の扱いは 2 案を比較した。採用した案は【要確認: 最終的に採用したパターン】
:::

::: figure 面談予約 → STEP3: ここで初めて認証 | 認証を後ろにずらし、フォーム入力中の離脱を防いだ
::: mockup phone src=/tmp-preview/img/tenshoku/counseling-complete.png src=/tmp-preview/img/tenshoku/step3-auth.png
::: caption 判定通過者は面談予約へ。予約完了からプロフィール入力へ誘導し、会員登録のタイミングで認証コードを求める
::: grid cols=2 gap=4
::: card 認証のタイミング
認証基盤への登録を「会員登録時」と「1 段目フォーム完了時」で比較し、会員登録時(STEP3)にまとめた
:::
---
::: card 重複登録の検知
会員登録時にメールアドレスで同一判定する。悪意ある入力を考慮し、同一判定と上書きは認証後に行う
:::
:::
:::

::: figure STEP4 → 完了: スカウト側の項目は後ろで | スカウト用の項目は「エージェントをより良く使うための追加情報」として依頼した
::: mockup phone src=/tmp-preview/img/tenshoku/step4-priority.png src=/tmp-preview/img/tenshoku/complete.png
::: caption STEP4 プロフィール入力(仕事探しで重視すること)→ 登録完了。1 回の登録で両サービスに登録される
:::

# 成果

## チームの成果

- 目標期日の前日、2025年9月29日に本番リリースした。
- メインフロー、新着スカウト0件時の画面、年収選択肢の変更箇所、「よくある質問」のデザインを確定させた。
- リリース後、新しい導線を通ってスカウト型サービスの登録まで到達するユーザーが生まれた。
- エージェント側のコンバージョン率・面談設定数を維持できたかは【要確認: ゴールに対する達成判定】。リリース前後で計測の定義が異なり、単純比較はできない。
