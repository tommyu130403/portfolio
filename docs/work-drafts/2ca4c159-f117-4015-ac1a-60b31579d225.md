# プロジェクト概要
::: summary
lead: キャリアチケットスカウトの開発チームで、施策の依頼から着手、効果検証までの進め方を作り直した。
problem: 施策とチームの規模が大きくなり、制作レビューの時間内に課題整理から要件整理、工数見積もりまでを終えられなくなった。
action: 振り返りで問題を言語化し、デザインドック・共有会の完了定義・工程の全体図とテンプレートを整えた。
result: 2026年時点でも共有会が定例で続き、同じ事業部のエージェントサービスにも広がった。
:::

中心は、デザインドック(取り組みの目的・ゴール・背景・要件・代替案などを1つにまとめ、チームの合意と決定の記録に使う文書)の導入と、共有会(旧・制作レビュー。職種を越えて依頼を検討する会議)の完了定義である。

| 段階 | 時期 | やったこと | 自分の担当 |
| --- | --- | --- | --- |
| 開発の振り返り | 2021年12月〜2022年1月 | 立ち上げ期の問題を7つに整理した | 振り返りの記録と課題の整理 |
| プロセスの文書化 | 2022年3月 | 工程ごとの現状・あるべき姿・アウトプットを1つの文書にまとめた | 文書化 |

| デザインドック導入 | 2023年10月〜 | デザインドック起点の依頼フローをつくった | 導入の決定、依頼フローとテンプレートの作成 |

# 役割
開発チームはプロダクトマネージャー、エンジニア、デザイナー、マーケターで構成される。2023年の体制見直しは、プロダクトマネージャー・エンジニア・デザイナーの代表3名で進めた。

自分はデザイナー代表として参加し、体制見直しの進行管理も担った。デザインドックの導入を提案して決め、仕組みづくりを主導した。時期ごとの担当は、プロジェクト概要の「進め方」の表にまとめた。

::: team 体制と、自分が兼ねた 2 つの役割
- 意思決定・進行 = Product, Project
- デザイン = Designer
- 開発 = Engineer
:::

# 背景と課題
## 背景

2021年のサービス立ち上げでは、根性論でスケジュールを守る状態が続いてしまった。振り返りでは「MVPと言いつつMVPではなく、機能を削る判断ができなかった」「仕様をデザインデータとシステム仕様書のどちらで管理するか決まっていない」といった問題が挙がった。

2023年には施策とチームの規模が大きくなり、制作レビューの時間内に課題整理から要件整理、工数見積もりまでを終えられなくなった。
依頼の情報が仕様書・デザインデータ・議事録などに分散し、レビューの場で会議のコストが必要以上に上がっていた。

## 課題の捉え直し

体制見直しでは、問題を「時間内に見積もれないこと」ではなく「**そもそも見積もれる情報が整形されていないこと**」と捉え直した。デザイナーの立場からは、網羅的な情報が常に反映された文書と、レビューの前に合意を取るプロセスが必要だと考えた。

::: figure 起きていたこと
| 問題 | 内容 |
| --- | --- |
| レビューの時間内に終わらない | 課題整理〜要件整理〜工数見積もりを、制作レビューの時間内で終えられなくなった |
| 見積もりに納得感がない | バッファを積むしかなく精度が下がる。見積もりの定義がそろっていない |
| 仕様の把握にコストがかかる | 依頼・仕様・デザインが別々のツールに散らばり、過不足に気づけない |
| レビュー一発合格が前提 | 依頼をそのままレビューに出し、その場で仕様をゼロから考えていた |
:::

# 取り組み
::: flow 取り組みの流れ numbered
- 振り返りで問題を言語化する
- 要求と要件を分け、デザインドックを導入する
- 共有会の「完了」を定義する
- 前後の工程まで1枚の図にする
- チームの分割とテンプレートの改訂
:::

### 1. 振り返りで問題を言語化する

立ち上げ期の開発を振り返り、問題を7つに整理した。

1. 開発環境が重い
2. ユーザーヒアリングが足りない
3. 根性論のスケジュール
4. MVPと言いつつMVPではなく、機能を削る判断ができなかった
5. 未経験の技術の見積もりと進め方
6. 仕様をデザインデータとシステム仕様書のどちらでどこまで管理するか
7. テストの進め方

最優先は根性論のスケジュールだ。対策として、要件の段階でリリース範囲をMVPからMLPまでの3パターンで定義し、計画の段階でスケジュールが崩れたときの代替プランを決めることにした。MVPを「サービスが使える」、MLPを「サービスが魅力的である」と定義した。そのうえで3つのパターンを3つの軸で比較した。

::: figure リリース範囲の3パターン比較 | 評価はS・A・B・Cの4段階(Sが最も高い)
| パターン | マーケティング | スピード | 改善 |
|---|---|---|---|
| 1. テストユーザーへのリリース | C | S | A |
| 2. 最小限でサービスが回る | A | B | B |
| 3. MLP(競合水準以上) | S | C | C |
:::

2022年3月には、工程ごとの現状・あるべき姿・アウトプットを1つの文書にまとめた。

### 2. 要求と要件を分け、デザインドックを導入する

体制見直しでは、依頼書と要件定義書を分ける方針にした。新しい価値をつくる場合はPRD(製品要求仕様書)、既存機能の改善はデザインドック、という手段の候補を出し、デザインドックの導入を決めた。依頼する側には「リソースがあるか」ではなく「どれだけ高い事業価値を最小の工数で出せるか」で考えてもらう。

::: flow 依頼の流れ highlight=1
- デザインドックを作成
- 事業責任者とすり合わせ
- 共有会(旧・制作レビュー)
- 依頼完了
:::

### 3. 共有会の「完了」を定義する

運用を始めると、「着手前に何を決めるか」「共有会で何をするか」の認識がそろっていないことがわかった。そこで、デザインドックを、「組織でデザイン(設計)する」ためにお互いを尊重して意思決定する土台と位置づけ、説明資料をつくった。
共有会を、読み合わせて認識をそろえる場ではなく、**各職種が目的に合った手段と観点を出して合意する場**として定義した。

共有会の完了は「目的に見合うコスト(工数×人数)がつかめている状態」と定義した。

::: figure コストを読み取る手がかり
| デザインドックの項目 | 読み取るもの |
| --- | --- |
| ゴールとユーザーストーリー | 求められる品質 |
| あえて含めないこと | 求められない品質 |
| 機能要件と代替案 | 必要な工数 |
:::

### 4. 前後の工程まで1枚の図にする

完了定義だけを共有しても、前後の工程が決まっていなければ納得感がない。そこで、施策の受け入れから効果検証までの全体図をつくり、会議ごとに「始めてよい条件」と「終わった条件」を決めた。

::: figure 施策の受け入れから効果検証まで
::: flow highlight=4
- 立案
- ドック作成
- 事業レビュー
- 共有会
- タスク作成
- 開発
- リリース
- 効果検証
:::

| 会議 | 始めてよい条件 | 終わった条件 |
| --- | --- | --- |
| 事業レビュー | デザインドックの項目が記載されている | 事業戦略に則っていることが承認される |
| 共有会 | 事業レビューを通過している。前日までにドックが共有されている | 投資してよいコスト(工数×人数)が確定している。見積もれない場合は暫定期日が示されている |
| タスク作成 | 共有会を通過している。期日と事業価値が着手時期にあわせて見直されている | 次の工程の担当者が着手できる |
:::

共有会では、見積もれない部分を調査の工数や暫定の期日で区切って前に進められるよう、会議中の意思決定に使うチャートを作成した。

あわせて、工程ごとにデザインドックのどの項目を誰が書くかを決め、タスクの受け入れ条件・完了定義のテンプレートもそろえた。

::: figure デザインドックは工程ごとに育てる | 依頼の時点ですべてを書き切らない
| 工程 | 誰が何を書くか |
| --- | --- |
| 依頼・相談(要求) | 依頼者がゴールと期日・あえて含めないこと・背景・ユーザーストーリー・成功指標・仮説・リスクを書く。機能要件は現時点のアイデアでよい |
| 要件の議論(要件) | デザイナー・エンジニアが機能要件と代替案を提案し、比較する |
| 提供方針の検討(設計) | 機能要件と代替案を見直し、再提案する |
| 効果検証 | 最終デザインと結果を反映する |
:::

### 5. チームの分割とテンプレートの改訂

エンジニアチームを企業向け・学生向け・エージェントサービスの3つに分けた際は、新しい会議を増やさず、既存の会議をチームごとに開く形で体制を組み直した。テンプレートは、期日とその理由を分けて書く形にした。各項目に記入のポイントを書き足し、エージェントサービス向けのチェックリストも加えた。

# 学び
開発中、「1か月の遅延が続くと、ビジネス価値を損なうだけでなく、関係者の離職や働き方にも影響する」と感じていた。
そのため、関係者の心理的安全性を守るためにも、振り返りと体制の見直しは定期的に行うべきだと実感した。

- ルールは、その前後の流れとセットで設計する必要がある。
- デザインドックは仕様書ではなく議論の土台として扱うことで、職種を越えて手段を出し合えるようになる。
