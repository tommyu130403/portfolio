# プロジェクト概要

キャリアチケットスカウトの2021年度の開発を振り返り、開発プロセスと組織の改善策をまとめた取り組みである。2022年1月に実施した。

# 役割

本プロジェクトの進行管理とデザイナーのリーダーとしてデザイン観点の改善点や問題点に関して洗い出しを行った。

# 背景と課題

## 背景

2021年度前半のβ版リリースの開発で、問題が多く表面化した。
今後円滑かつ継続的な開発体制を取っていくためにも、次の段階である正規版の開発に進む前に各領域の課題を洗い出すタイミングであると判断した。
( 開発環境、テスト、スケジュール、プロジェクトの認識、仕様管理 etc..)

# 取り組み

::: flow 進め方 highlight=0
- ヒアリングと問題の洗い出し
- 根本原因の分析
- 対策の設計
:::

### ヒアリングと問題の洗い出し

関係者7名にヒアリングし、問題を7件に整理した。

1. 開発環境が重い
2. ユーザーヒアリングが足りない
3. 根性論のスケジュール
4. MVPと言いつつMVPではなく、機能を削る判断ができなかった
5. 未経験の技術の見積もりと進め方
6. 仕様をデザインツールとシステム仕様書のどちらでどこまで管理するか
7. テストの進め方

### 根本原因の分析

最優先とした根性論のスケジュールについて、原因を整理した。仕様を考えながら実装していた。開発文化やスタンスの定義が曖昧で、柔軟に動きすぎた。「MVPかも」と思い、引き算ができなかった。

### 対策の設計

MVPを「サービスが使える」、MLPを「サービスが魅力的である」と定義した。そのうえでMVPを3パターンに分け、3軸で比較した。

::: figure MVP の 3 パターン比較
| パターン | マーケティング | スピード | 改善 |
|---|---|---|---|
| 1. テストユーザーへのリリース | C | S | A |
| 2. 最小限でサービスが回る | A | B | B |
| 3. MLP(競合水準以上) | S | C | C |
:::

- 要件フェーズでMVP/MLPを定義し、計画フェーズで代替プランを定義する
- 技術選定ルール: 未経験で予測が立たない技術は選ばない。有識者をアサインできない、またはサポーターとして迎えられない場合も選ばない
- 開発環境はDocker導入で様子を見る

# 成果

スケジュールの問題を個人の頑張りに依存させないため、要件・計画フェーズでMVPと代替プランを定義する体制を、ルールとして取り決めた。

# 学び

開発中、「1か月遅延の状態が続くことは、単にビジネス価値を損なうだけでなく、関わる関係者の離職や働き方に影響してしまう」と感じていた。
そのため、今回の改善と定義において関係者の「心理的安全性」が担保されることを目的として丁寧に振り返りと体制改善につなげることは定期的に実施すべきだと実感した。
