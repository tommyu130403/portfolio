# プロジェクト概要

キャリアチケットスカウトの開発チームで、施策の依頼から着手、効果検証までの進め方を作り直した取り組みである。中心に置いたのは「デザインドック」だ。施策の目的・背景・仮説・要件・検討した代替案を1つの文書にまとめ、職種の違うメンバーが同じ文書の上で議論し、合意してから着手する。

2021年末の開発振り返りから始めた。2023年に体制を見直してデザインドックを導入し、2024年に共有会の完了定義と工程全体の図をつくった。2025年にテンプレートを改訂した。運用は2026年時点でも定例として続いており、同じ事業部のエージェントサービスにも広がっている。

# 役割

開発チームはプロダクトマネージャー、エンジニア、デザイナー、マーケターで構成される。2023年の体制見直しは、プロダクトマネージャー・エンジニア・デザイナーの代表3名で進めた。

自分はデザイナー代表として参加し、デザインドックの導入を決めて、仕組みづくりを主導した。

- 開発振り返りの記録と課題の整理（2021〜2022年）
- 開発プロセスの文書化（2022年）
- 体制見直しの課題抽出・進行管理・まとめ、開発手法の調査（2023年）
- デザインドック導入の決定と、デザインドック起点の制作依頼フローの作成（2023年）
- デザインドックの役割を説明する資料の作成と、共有会の完了定義の提案（2024年）
- 施策の受け入れから効果検証までの全体図の作成（2024年）
- エンジニアチームの分割にあわせた体制の再設計への参加（2024年）
- デザインドックのテンプレートの作成と改訂（2025年）

# 背景と課題

## 背景

2021年のサービス立ち上げでは、仕様を考えながら実装し、根性論でスケジュールを守る状態が続いた。振り返りでは「MVPと言いながら機能を削る判断ができなかった」「仕様をデザインデータとシステム仕様書のどちらで管理するか決まっていない」といった問題が挙がった。

2023年には施策とチームの規模が大きくなった。制作レビューの時間内に、課題整理から要件整理、工数見積もりまでを終えられなくなった。依頼はタスク管理ツールにそのまま書かれ、レビューの場で仕様をゼロから考えていた。仕様はタスク管理ツール・システム仕様書・デザインデータに散らばり、過不足に気づけなかった。

## 課題の捉え直し

体制見直しでは、問題を「時間内に見積もれないこと」ではなく「そもそも見積もれる情報が整形されていないこと」と捉え直した。デザイナーの立場からは、網羅的な情報が常に反映された文書と、レビューの前に合意をとるプロセスが必要だと考えた。

::: figure 起きていたこと
| 問題 | 内容 |
| --- | --- |
| レビューの時間内に終わらない | 課題整理〜要件整理〜工数見積もりを、制作レビューの時間内で終えられなくなった |
| 見積もりに納得感がない | バッファを積むしかなく精度が下がる。見積もりの定義がそろっていない |
| 仕様の把握にコストがかかる | 依頼・仕様・デザインが別々のツールに散らばり、過不足に気づけない |
| レビュー一発合格が前提 | 依頼をそのままレビューに出し、その場で仕様をゼロから考えていた |
:::

# 取り組み

### 1. 振り返りで問題を言語化する

立ち上げ期の開発を振り返り、問題を7つに整理した。

1. 開発環境が重い
2. ユーザーヒアリングが足りない
3. 根性論のスケジュール
4. MVPと言いつつMVPではなく、機能を削る判断ができなかった
5. 未経験の技術の見積もりと進め方
6. 仕様をデザインデータとシステム仕様書のどちらでどこまで管理するか
7. テストの進め方

最優先は根性論のスケジュールだ。対策として、要件の段階でMVPを3パターンで定義し、計画の段階でスケジュールが崩れたときの代替プランを決めることにした。MVPを「サービスが使える」、MLPを「サービスが魅力的である」と定義した。そのうえで3つのパターンを3つの軸で比較した。

::: figure MVP の 3 パターン比較
| パターン | マーケティング | スピード | 改善 |
|---|---|---|---|
| 1. テストユーザーへのリリース | C | S | A |
| 2. 最小限でサービスが回る | A | B | B |
| 3. MLP(競合水準以上) | S | C | C |
:::

翌年には、工程ごとの現状・あるべき姿・アウトプットを1つの文書にまとめた。

### 2. 要求と要件を分け、デザインドックを導入する

体制見直しでは、依頼書と要件定義書を分ける方針にした。新しい価値をつくる場合はPRD（製品要求仕様書）、既存機能の改善はデザインドック、という手段の候補を出し、デザインドックの導入を決めた。依頼する側には「リソースがあるか」ではなく「どれだけ高い事業価値を最小の工数で出せるか」で考えてもらう。

::: flow 依頼の流れ highlight=1
- デザインドックを作成
- 事業責任者とすり合わせ
- 制作レビュー
- 依頼完了
:::

### 3. 共有会の「完了」を定義する

運用を始めると、「着手前に何を決めるか」「共有会で何をするか」の認識がそろっていなかった。そこで、デザインドックを「組織でデザイン（設計）する」ために、お互いを尊重して意思決定するものと位置づけ、説明資料をつくった。読み合わせて認識をそろえる場ではなく、各職種が目的に合った手段と観点を出して合意する場である。

共有会の完了は「目的に見合うコスト（工数×人数）がつかめている状態」と定義した。

::: figure コストを読み取る手がかり
| デザインドックの項目 | 読み取るもの |
| --- | --- |
| ゴールとユーザーストーリー | 求められる品質 |
| あえて含めないこと | 求められない品質 |
| 機能要件と代替案 | 必要な工数 |
:::

### 4. 前後の工程まで1枚の図にする

完了定義だけを共有しても、前後の工程が決まっていなければ納得感がない。そこで、施策の受け入れから効果検証までの全体図をつくり、会議ごとに「始めてよい条件」と「終わった条件」を決めた。

::: figure 施策の受け入れから効果検証まで
::: flow highlight=4
- 立案
- ドック作成
- 事業レビュー
- 共有会
- タスク作成
- 開発
- リリース
- 効果検証
:::

| 会議 | 始めてよい条件 | 終わった条件 |
| --- | --- | --- |
| 事業レビュー | デザインドックの項目が記載されている | 事業戦略に則っていることが承認される |
| 共有会 | 事業レビューを通過している。前日までにドックが共有されている | 投資してよいコスト（工数×人数）が確定している。見積もれない場合は暫定期日が示されている |
| タスク作成 | 共有会を通過している。期日と事業価値が着手時期にあわせて見直されている | 次の工程の担当者が着手できる |
:::

共有会では、見積もれない部分を調査の工数や暫定の期日で区切り、前に進める判断の流れを示した。

::: figure 共有会の中の判断の流れ | 仕様が確定するまで待たず、区切って前に進める
| 問い | はい | いいえ |
| --- | --- | --- |
| 1. 機能要件が確定できるか | 2へ | 不足している情報を集める。制作側の調査が要るなら3へ |
| 2. 全体の工数が見積もれるか | 工数を見積もって完了 | 3へ |
| 3. 調査の工数が見積もれるか | 調査の工数だけ見積もって着手 | 4へ |
| 4. 工数が未知数でも進める価値があるか | 暫定期日を決めて着手 | 事業価値から見直す |
:::

あわせて、工程ごとにデザインドックのどの項目を誰が書くかと、タスクの受け入れ条件・完了定義のテンプレートもそろえた。

::: figure デザインドックは工程ごとに育てる | 依頼の時点ですべてを書き切らない
| 工程 | 誰が何を書くか |
| --- | --- |
| 依頼・相談（要求） | 依頼者がゴールと期日・あえて含めないこと・背景・ユーザーストーリー・成功指標・仮説・リスクを書く。機能要件は現時点のアイデアでよい |
| 要件の議論（要件） | デザイナー・エンジニアが機能要件と代替案を提案し、比較する |
| 提供方針の検討（設計） | 機能要件と代替案を見直し、再提案する |
| 効果検証 | 最終デザインと結果を反映する |
:::

### 5. チームの分割とテンプレートの改訂

エンジニアチームを企業向け・学生向け・エージェントサービスの3つに分けた際は、新しい会議を増やさず、既存の会議をチームごとに開く形で体制を組み直した。テンプレートは、期日とその理由を分けて書く形にした。各項目に記入のポイントを加え、エージェントサービス向けのチェックリストも加えた。

# 学び

開発中、「1か月遅延の状態が続くことは、単にビジネス価値を損なうだけでなく、関わる関係者の離職や働き方に影響してしまう」と感じていた。
そのため、今回の改善と定義において関係者の「心理的安全性」が担保されることを目的として丁寧に振り返りと体制改善につなげることは定期的に実施すべきだと実感した。

- 完了の定義だけを示しても、前後の工程がつながっていなければ納得してもらえない。ルールは、その前後の流れとセットで設計する必要がある。
- デザインドックは仕様書ではなく議論の土台として扱うことで、職種を越えて手段を出し合えるようになる。
- 残っている課題もある。効果検証の結果まで書き切られた施策はまだ少ない。機能要件の欄に技術的な詳細が増え、技術仕様書に近づく傾向もある。仮説を検証して次の施策につなげる部分を仕組みにすることが、次の課題だ。
