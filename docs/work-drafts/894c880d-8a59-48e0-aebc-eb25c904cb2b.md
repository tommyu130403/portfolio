# プロジェクト概要

スカウト型の新卒就活サービス「キャリアチケットスカウト」の立ち上げに、初期機能の検討からデザインリード兼PMとして関わった。学生が自己分析とプロフィール入力を進めると企業からスカウトが届く仕組みの初期範囲を、ヒアリングと会議を重ねて決めた。

事業の狙いは、同サービスのエージェント事業(キャリアチケット就職エージェント)でカウンセラーが担ってきた「強みを見つける・軸を固める」支援を、プロフィール入力の機能に置き換えることだった。これにより、人を介さずに学生と企業をマッチングできるようにする。

2021年8月に学生向けアプリ、11月に企業向けWebアプリをリリース。

# 背景と課題

## 背景・課題
これまで支援できていたのは「1000人未満の、認知度の低い企業」で、学生が普通に探していては出会えないセグメントだった。母集団としての規模に上限があり、今後事業を拡張していく上でさらに支援できる範囲を広げていく必要があった。

::: figure 事業の狙い | 収益源である人材紹介(カウンセリング)主体のサービスでは、早期に動き出す学生に届かなかった
::: beforeafter 人材紹介主体からスカウト型へ
before: 人材紹介(カウンセリング)主体 → [!早期に動く学生に価値を出せない] → リード獲得が困難
note: 就活時期の早い学生ほど、カウンセリングの前にサービスから離れていた
after: アドバイザーを介さないスカウト型 → [+就活時期を問わずシェアを広げる] → 収益化の機会が増える
note: 学生側は満足度を担保しつつ「ファンづくり・認知」を、企業側は購買〜継続利用のファネルを設計する
:::
::: caption 出典: 企画書「ビジネスターゲット」
:::

## 体制と進め方
- デザイナーが自分1人(約1人月)では、計画どおりのリリースに少なくとも追加で1人月以上が必要と見積もった。必要なスキルと参画時期を整理したうえで、事業責任者に人件費の追加投資を提案した。
- プロジェクトスコープが曖昧にならないように、PMとしてプロジェクト憲章(目的やビジネス価値など)をあらかじめまとめ責任者や関係者と合意形成を取った。
- デザインシステムとCSS設計(カラー定義・コンポーネント設計・CSS Modules)の検討をエンジニアとともに実施した。主にフロントエンドの実装範囲はデザイナーが担当することとなっていた。

## リサーチ
人事・RA(企業の採用を支援する営業担当)の視点を持つ2名とカウンセラー1名へのヒアリングの記録を作成した。学生向けのテストも設計し、2021年5月に学生計3名に実施した。
- 企業側からは、一番ほしい学生情報は「基本情報・自己PR・長所短所・写真」であること、希望条件は途中で変わっても入れ直されないので信用しにくいことが挙がった。
- カウンセラーからは、強みは3つ出させるより「アピールポイント」として引き出すほうがよい、という意見を得た。
- 学生テストは、使い勝手ではなく機能への印象を聞くのが目的。Figma のプロトタイプを Zoom で共有し、発言をその場でプロトタイプにコメントで残す方式で設計した。

::: workcard id=e68325ec-bb35-413a-9a89-3141a754217f

## β版の範囲
初期機能すり合わせでは「自己分析フロー」「『気になる』の表記」「希望勤務地の有無」の検討を担当した。
- 強みは「アピールポイント」として項目化した。就活の軸は最大3つ設定して企業にメインで見せるものを1つ選ぶ「タイトル＋根拠」の型にし、ガクチカ(学生時代に力を入れたこと)には選択式のカテゴリを加えた。
- 適性検査はエゴグラムを採用し、受験が1回だけであることを注意書きで示した。
- 希望業種・希望職種は「サービスの目的から逆行する」として削った。企業の要望が多かった候補者リストも、期日までに「まずスカウトができる」状態を出すことを優先して見送った。

::: figure 自己分析の思考フレーム | 「客観 → 主観 → 分析 → アウトプット」の順に、到達したい状態を積み上げる設計
::: flow highlight=0
- 適性検査
- 自分史
- ガクチカ
- 強み
- 就活の軸
- 自己PR
:::

| 段階 | 到達したい状態 |
| --- | --- |
| 適性検査(客観) | 定量的に自分の特性を理解している |
| 自分史(主観) | 今までの行動が洗い出されている |
| ガクチカ | 力を入れたことを具体的に書けている |
| 強み | 自分の強みをいくつか言語化できている |
| 就活の軸 | 会社・仕事選びの自分なりの基準が明確になっている |
| 自己PR | 結論と根拠(エピソード)で 300〜400 字にまとまる |

::: caption 「強み」は他者より優れた能力ではなく、自分の能力の中で最も優れたもの、と定義した。出典: 自己分析フレームの検討図
:::

::: figure アプリ内の入力ルール | ストックした情報をアウトプットとして管理できるよう、数と文字数を決めた

| 機能 | 上限 |
| --- | --- |
| 自分史・経験カード | 無制限 |
| ガクチカ | 500 文字 × 最大 3 つ |
| 強み | 15 文字 × 最大 5 つ(3 つ推奨) |
| 自己PR | 500 文字 × 1 つ |

::: caption 自己PRが書けない学生は、自分史の洗い出しから始める分岐にした。出典: アプリ内ユーザー行動の設計図
:::

**正規版の範囲決め**:
学生詳細で学生を続けて見る方法として、カルーセル・遷移ボタン・写真のマウス追従の3案を比べた。プッシュ通知は利用状況を根拠に範囲から外し、部分対応の余地を残した。

正規版は一括ではなく、機能を順次リリースする方針となった。

### 入力項目の削減

高校、希望職種、希望業種、企業タイプ、他社選考状況、短所、資格、SNSログインを削除した。希望業種・職種は「サービス目的から逆行する」として不要と判断した。

### 主な機能仕様

| 学生側 | 登録と学生認証、経験、自己分析(やりたいこと・できること・やるべきこと、学生時代に力を入れたこと、強み)、適性検査(1回のみ受験)、他己分析、就職活動状況。学生時代に力を入れたことはカテゴリの選択式とし、就活の軸は最大3つ・メイン1つとした |
| 企業側 | 上限付きの複数アカウント、オファー数・承諾数の上限ルール、従量課金 |

# 成果

- 2021年8月に学生向けアプリを、11月に企業向けWebアプリをリリースした(企業側は計画から約2か月遅れ)。MVPの機能はすべて実装できた。
- β版で検証した「自己分析をしながらスカウトがもらえる」というベネフィットは、リリース後のユーザーヒアリングで、学生への訴求として十分ではないとわかった。学生は自己分析が重要なことは知っていても、なぜ重要かは理解していなかった。

# 学び

2021年度前半の開発をチームで振り返り、問題を洗い出した。
- 「MVPと言っていたけどMVPじゃなかった」「機能を削る判断ができなかった」ことが、無理のあるスケジュールの原因として挙がった。
- うまく機能した点として、テストに開発以外の人をアサインしたことが挙がった。

::: card tone=accent 対策
要件フェーズで MVP(サービスが使える)と MLP(サービスが魅力的である)を定義し、計画フェーズでスケジュール調整の代替案を決めておく。状況に合わせた意思決定ができる状態を先につくる。
:::
